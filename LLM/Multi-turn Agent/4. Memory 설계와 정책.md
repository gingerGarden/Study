# 4. Memory 설계와 정책

Memory는 Agent가 세션을 넘어 정보를 유지하는 기능입니다. 단순히 과거 대화를 저장하는 것이 아니라, 장기적으로 다시 사용할 가치가 있는 정보를 추출, 검증, 검색, 갱신, 삭제하는 체계입니다.

## 4.1. Memory의 종류

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| Short-term Memory | 현재 세션의 최근 문맥 | 최근 N턴 |
| Working Memory | 현재 작업의 중간 상태 | 검색 조건, 진행 단계 |
| Long-term Memory | 장기간 유지할 정보 | 사용자 선호, 프로젝트 설정 |
| Semantic Memory | 의미 검색 가능한 지식 | 요구사항, 결정사항 |
| Episodic Memory | 과거 작업 이력 | 지난번 생성한 보고서 |

실무에서는 Working Memory는 State Store에, Long-term과 Semantic Memory는 별도 Memory Store에 두는 경우가 많습니다.

## 4.2. Memory 추출 기준

모든 대화를 Memory로 저장하면 품질이 낮아집니다. 다음 기준을 만족하는 정보만 저장해야 합니다.

* 앞으로 반복 사용될 가능성이 있음
* 사용자가 명시적으로 선호나 결정을 표현함
* 프로젝트나 업무 규칙에 영향을 줌
* 출처 메시지를 추적할 수 있음
* 개인정보 저장 정책을 위반하지 않음

예시는 다음과 같습니다.

```json
{
  "content": "사용자는 보고서 형식의 답변을 선호한다.",
  "memory_type": "preference",
  "scope": "user",
  "importance": 0.7,
  "source_message_id": "msg_42",
  "status": "active"
}
```

## 4.3. Memory 검색

현재 요청에 관련된 Memory만 프롬프트에 포함해야 합니다.

```
현재 사용자 요청
  ↓
Embedding 생성
  ↓
Vector DB 검색
  ↓
관련도, 최신성, 중요도 기준 재정렬
  ↓
상위 K개 선택
  ↓
프롬프트에 삽입
```

검색 기준은 단순 유사도만으로 충분하지 않습니다.

| 기준 | 이유 |
| --- | --- |
| 유사도 | 현재 요청과 의미적으로 관련 있는지 판단 |
| 최신성 | 오래된 결정이 현재와 충돌할 수 있음 |
| 중요도 | 핵심 결정사항을 우선 사용 |
| 범위 | 사용자, 프로젝트, 조직 단위 구분 |
| 상태 | active, replaced, deleted 구분 |

## 4.4. 충돌 관리

Memory는 시간이 지나며 충돌할 수 있습니다.

```
과거 Memory:
백엔드는 Flask를 사용한다.

현재 사용자 지시:
백엔드는 FastAPI로 바꾸자.
```

이 경우 과거 Memory를 물리 삭제하기보다 상태를 변경하는 방식이 좋습니다.

```json
{
  "old_memory_id": "mem_10",
  "status": "replaced",
  "replaced_by": "mem_25"
}
```

최신 사용자 지시가 명확하면 최신 내용을 우선하고, 모호하면 확인 질문을 해야 합니다.

## 4.5. 삭제와 개인정보

사용자는 Memory를 확인, 수정, 삭제할 수 있어야 합니다.

필수 기능은 다음과 같습니다.

* 저장된 Memory 목록 조회
* 특정 Memory 삭제
* 특정 범위의 Memory 비활성화
* 민감정보 저장 방지
* Memory 출처 확인

개인정보나 민감정보가 포함될 수 있는 Agent에서는 Memory 저장을 기본값으로 켜기보다, 명시적인 정책과 동의 흐름을 두는 것이 안전합니다.
