# 4. Semantic Memory 방식
과거 대화에서 장기적으로 필요한 사실을 추출하여 Embedding으로 저장하고, 현재 질문과 관련된 기억만 검색하는 방식입니다.

```
대화 발생
    ↓
기억 후보 추출
    ↓
Embedding 생성
    ↓
Vector DB 저장
    ↓
현재 질문과 유사한 기억 검색
    ↓
검색된 기억을 프롬프트에 삽입
```

예를 들어 다음 기억이 저장되어 있다고 가정합니다.

```json
{
  "content": "사용자는 검색 결과에 근거 논문과 관련도 점수가 포함되기를 원한다.",
  "memory_type": "requirement",
  "importance": 0.9
}
```

나중에 사용자가 다음과 같이 요청합니다

```
검색 API 응답 구조를 작성해줘.
```

현재 요청과 관련된 기억을 검색하여 다음과 같이 전달합니다

```
[관련 기억]

- 검색 결과에는 근거 논문이 포함되어야 한다.
- 각 검색 결과에는 관련도 점수가 포함되어야 한다.
- 최대 검색 결과 수는 100건이다.
```

### 장점
* 여러 세션에 걸친 장기 기억을 구현할 수 있음
* 현재 요청과 관련된 정보만 사용하므로 토큰 효율이 좋음
* 사용자 선호와 프로젝트 정보를 재활용할 수 있음
* 대화가 많아져도 검색 기반으로 확장할 수 있음

### 단점
* 관련 기억을 검색하지 못할 수 있음
* 현재 상황과 무관한 기억이 검색될 수 있음
* 과거 정보와 최신 정보의 충돌 관리가 필요함
* 잘못 추출된 기억이 장기간 남을 수 있음
* 개인정보와 기억 삭제 정책이 필요함

Semantic Memory만으로는 “그걸로 진행해”처럼 직전 대화에 의존하는 표현을 해석하기 어렵습니다. 따라서 최근 N턴 방식과 함께 사용해야 합니다.

Memory로 저장할 내용과 저장하지 않을 내용을 구분해야 합니다.

| 저장하기 좋은 정보 | 저장하지 않는 편이 좋은 정보 |
| --- | --- |
| 반복적으로 사용되는 사용자 선호 | 일회성 잡담 |
| 프로젝트의 확정된 기술 스택 | 임시로 검토한 선택지 |
| 장기적으로 필요한 업무 규칙 | 민감하거나 불필요한 개인정보 |
| 사용자가 명시적으로 저장을 요청한 정보 | 출처가 불명확한 추론 |

Memory 항목에는 내용뿐 아니라 출처, 중요도, 상태를 같이 저장하는 것이 좋습니다.

```json
{
  "id": "mem_1024",
  "content": "사용자는 검색 결과를 관련도순으로 정렬하기를 원한다.",
  "memory_type": "preference",
  "importance": 0.8,
  "source_message_id": "msg_77",
  "created_at": "2026-07-29T10:00:00+09:00",
  "status": "active"
}
```

검색된 Memory를 그대로 프롬프트에 넣기보다 현재 요청과의 관련성을 한 번 더 평가하는 과정이 필요할 수 있습니다.

```
1. 현재 요청으로 후보 Memory 검색
2. 관련도와 최신성을 기준으로 재정렬
3. 충돌하는 Memory가 있으면 최신 active 항목 우선
4. 상위 K개만 프롬프트에 삽입
```

장기 기억을 제공하는 Agent는 사용자가 기억을 확인, 수정, 삭제할 수 있는 기능도 고려해야 합니다.
