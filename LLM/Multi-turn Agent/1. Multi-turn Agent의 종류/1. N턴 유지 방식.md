# 1. N턴 유지 방식
최근 N개의 메시지 또는 N회의 대화만 LLM에 전달

```python
from collections import deque
from typing import TypedDict


class Message(TypedDict):
    role: str
    content: str


recent_messages: deque[Message] = deque(maxlen=10)


def add_message(role: str, content: str) -> None:
    recent_messages.append(
        {
            "role": role,
            "content": content,
        }
    )
```

최근 메시지 10개를 유지한다면 사용자와 Assistant의 왕복 기준으로 약 5턴을 보관합니다.

실제 구현에서는 System Prompt와 Agent State는 N턴 제한 대상에서 제외하는 것이 일반적입니다.

```python
def build_prompt(
    system_prompt: str,
    state: dict,
    recent_messages: list[Message],
    user_input: str,
) -> list[dict]:
    return [
        {
            "role": "system",
            "content": system_prompt,
        },
        {
            "role": "system",
            "content": f"Current state: {state}",
        },
        *recent_messages,
        {
            "role": "user",
            "content": user_input,
        },
    ]
```

최근 대화는 직전 지시어를 해석하는 데 특히 중요합니다.

```
사용자: 첫 번째 방식은 너무 복잡해.
Agent: 그럼 두 번째 방식으로 진행하겠습니다.
사용자: 그걸 코드로 보여줘.
```

이때 "그걸"은 최근 대화 없이는 해석하기 어렵습니다.

### 장점
* 구현이 간단함
* 토큰 사용량을 일정하게 제한할 수 있음
* 최근 문맥을 정확하게 유지함
* 응답 속도와 비용을 예측하기 쉬움

### 단점
* 오래된 중요한 정보도 N턴이 지나면 사라짐
* 장기 프로젝트에는 부적합함
* 과거 결정사항을 사용자가 다시 설명해야 할 수 있음

### 사용하기 적합한 경우
* 고객 상담처럼 최근 맥락이 가장 중요한 경우
* 빠른 프로토타입을 만들 때
* 사용자의 요청이 짧은 세션 안에서 끝나는 경우
* 별도 DB나 Memory 시스템 없이 시작해야 하는 경우

### 구현 시 주의점
* 메시지 개수 기준과 턴 기준을 혼동하지 않아야 함
* Tool 호출 결과가 길다면 원문 전체 대신 요약 또는 참조 ID를 넣어야 함
* 오래된 확정 사항은 Agent State나 요약본으로 따로 승격해야 함
* 너무 작은 N은 지시어 해석 실패를 늘리고, 너무 큰 N은 비용과 지연시간을 증가시킴
