# 0. 정리 및 비교

## 일반적으로 권장되는 혼합 구조
실제 Multi-turn Agent에서는 하나의 방식만 사용하기보다 여러 방식을 결합합니다.

```
System Prompt
    +
구조화된 Agent State
    +
누적 대화 요약본
    +
Semantic Memory 검색 결과
    +
최근 N턴 원문
    +
현재 사용자 요청
```

각 요소의 역할은 다음과 같습니다.

| 구성 요소           | 역할                  |
| --------------- | ------------------- |
| System Prompt   | Agent의 역할과 행동 원칙    |
| Agent State     | 현재 작업 단계와 확정된 조건    |
| 대화 요약           | 장기적인 대화 흐름          |
| Semantic Memory | 과거의 관련 요구사항과 사용자 정보 |
| 최근 N턴           | 직전 문맥과 지시어 해석       |
| 현재 요청           | 가장 우선하는 사용자 지시      |

방식별 특성을 비교하면 다음과 같습니다.

| 방식 | 강점 | 약점 | 적합한 업무 |
| --- | --- | --- | --- |
| 전체 대화 이력 | 구현이 가장 단순함 | 긴 세션에서 비용과 토큰 증가 | 데모, 짧은 상담 |
| 최근 N턴 | 비용 예측이 쉬움 | 오래된 정보 손실 | 짧은 세션 챗봇 |
| 대화 요약본 | 긴 흐름 유지 | 요약 누락과 왜곡 가능 | 장시간 상담, 문서 작업 |
| 구조화된 State | 확정 조건 관리 | 스키마 설계 필요 | 신청, 검색, 분석 업무 |
| Semantic Memory | 세션 간 기억 | 검색 실패와 충돌 관리 필요 | 개인화, 프로젝트 기억 |
| 슬롯 기반 | 필수 입력 누락 방지 | 유연성 낮음 | 예약, 신청서, 조건 입력 |
| Workflow | 절차 통제 | 설계와 유지보수 부담 | 기업 업무 자동화 |
| ReAct | 도구 기반 반복 수행 | 루프와 비용 통제 필요 | 검색, 분석, 계산 |
| Plan-and-Execute | 복잡한 작업 관리 | 계획 오류 가능 | 연구, 보고서, 장기 작업 |

도구 실행 구조까지 포함하면 다음과 같습니다.

```
                        ┌────────────────────┐
사용자 입력 ───────────→│ Agent Controller   │
                        └─────────┬──────────┘
                                  │
                ┌─────────────────┼─────────────────┐
                ▼                 ▼                 ▼
          최근 대화 조회       State 조회       Memory 검색
                │                 │                 │
                └─────────────────┼─────────────────┘
                                  ▼
                          Prompt 구성 및 LLM 호출
                                  │
                         ┌────────┴────────┐
                         ▼                 ▼
                    사용자 응답        Tool 호출
                                           │
                                           ▼
                                      실행 결과 검증
                                           │
                                           ▼
                              State·History·Memory 갱신
```

## 구현 시 중요한 설계 원칙

## 최신 사용자 지시를 가장 우선해야 함

정보가 충돌할 때는 일반적으로 다음 우선순위를 적용합니다.

```
현재 사용자 지시
> 최근 대화에서 확정된 사항
> 최신 Agent State
> Semantic Memory
> 과거 대화 요약
```
예를 들어 과거에는 Streamlit을 사용하기로 했더라도 사용자가 현재 React로 변경하라고 요청하면 최신 요청을 반영해야 합니다.

다만 최신 지시가 모호하면 바로 State를 변경하지 말고 확인 질문을 해야 합니다.

```
사용자: 아까 말한 조건은 빼줘.
Agent: 검색 기간 조건을 제외한다는 의미인가요, 결과 수 제한을 제외한다는 의미인가요?
```

명확한 변경은 즉시 반영하고, 모호한 변경은 확인 후 반영하는 것이 안전합니다.

## 대화 기록과 사실을 구분해야 함

다음 대화 원문을 그대로 Memory로 저장하는 것보다:

```
사용자: 백엔드는 FastAPI가 제일 나을 것 같아.
```

다음과 같이 정제하는 편이 좋습니다.

```
해당 프로젝트의 백엔드 프레임워크는 FastAPI로 결정되었다.
```

다만 사용자가 단순히 의견을 말한 것인지 최종 결정을 내린 것인지 구분해야 합니다.

## Memory에는 출처와 시간을 저장해야 함

```json
{
  "content": "백엔드는 FastAPI를 사용한다.",
  "memory_type": "decision",
  "source_message_id": "msg_1024",
  "created_at": "2026-07-29T10:00:00+09:00",
  "status": "active"
}
```

과거 기억이 변경되면 기존 기억을 삭제하기보다 비활성화하거나 새로운 기억이 이전 기억을 대체한다는 관계를 저장하는 것이 좋습니다.

## 도구 호출은 백엔드에서 검증해야 함
LLM이 다음과 같은 도구 호출을 생성했다고 하더라도 그대로 실행하면 안 됩니다.

```
{
  "tool": "search_papers",
  "arguments": {
    "start_year": 2030,
    "end_year": 2020,
    "result_limit": -100
  }
}
```
백엔드에서 입력값을 검증해야 합니다.

```python
from pydantic import BaseModel, Field, model_validator


class PaperSearchInput(BaseModel):
    query: str = Field(min_length=1)
    start_year: int
    end_year: int
    result_limit: int = Field(default=100, ge=1, le=1_000)

    @model_validator(mode="after")
    def validate_year_range(self) -> "PaperSearchInput":
        if self.start_year > self.end_year:
            raise ValueError("start_year는 end_year보다 클 수 없습니다.")

        return self
```

## 반복 횟수와 종료 조건이 필요함
Agent가 계속 도구를 호출하는 것을 막기 위해 다음과 같은 제한을 두는 것이 좋습니다.

```python
MAX_AGENT_ITERATIONS = 8
MAX_TOOL_RETRIES = 2
MAX_REPLANS = 1
```

종료 조건도 명시해야 함

```
- 사용자 요청이 충족됨
- 더 이상 실행할 도구가 없음
- 최대 반복 횟수에 도달함
- 복구할 수 없는 오류가 발생함
- 추가 사용자 정보가 반드시 필요함
```

## 현실적인 개발 단계
처음부터 복잡한 Semantic Memory와 자율 Agent를 모두 구현하기보다는 단계적으로 확장하는 것이 좋습니다.

프로젝트 초기에는 다음 기준으로 시작점을 정할 수 있습니다.

| 상황 | 추천 시작 구조 |
| --- | --- |
| 빠른 프로토타입 | 최근 N턴 + System Prompt |
| 입력 조건이 명확함 | 최근 N턴 + 슬롯 기반 State |
| 긴 문서 작업 | 최근 N턴 + 대화 요약본 |
| 검색/API 연동 | 최근 N턴 + Tool Calling + 입력 검증 |
| 장기 개인화 | 최근 N턴 + Semantic Memory |
| 기업 업무 자동화 | State Machine + Tool Calling + 검증 |

### 1단계: 기본 Multi-turn
```
최근 N턴
+ 간단한 System Prompt
+ 단일 LLM 호출
```

우선 대화 문맥이 자연스럽게 유지되는지 확인합니다.

<br>

### 2단계: 구조화된 State
```
최근 N턴
+ 업무별 Agent State
+ 입력값 검증
```
사용자의 요구사항과 작업 진행 상태를 구조화합니다.

<br>

### 3단계: 대화 요약

```
최근 N턴
+ 누적 요약
+ Agent State
```

긴 대화에서도 문맥을 유지하도록 확장합니다.

<br>

### 4단계: Tool Calling

```
LLM
+ API
+ 데이터베이스
+ 검색
+ 파일 처리
```
도구의 입력·출력을 명시적인 스키마로 정의합니다.

<br>

### 5단계: Semantic Memory

```
Memory 추출
+ Vector DB 저장
+ 관련 기억 검색
+ 기억 충돌 및 삭제 관리
```
여러 세션에 걸친 장기 기억을 구현합니다.

<br>

### 6단계: Workflow Agent
```
Plan
+ Execute
+ Validate
+ Retry
+ State Machine
```
복잡한 업무를 단계적으로 수행하고 실패 시 복구하도록 구성합니다.
