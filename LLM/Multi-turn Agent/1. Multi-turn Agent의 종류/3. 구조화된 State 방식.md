# 3. 구조화된 State 방식
대화에서 중요한 정보를 JSON이나 데이터 모델로 추출하여 관리하는 방식입니다.

```python
from pydantic import BaseModel, Field


class PaperSearchState(BaseModel):
    query: str | None = None
    start_year: int | None = None
    end_year: int | None = None
    result_limit: int = 100
    classification_method: str | None = None
    completed_steps: list[str] = Field(default_factory=list)
    pending_steps: list[str] = Field(default_factory=list)
```

대화가 진행될 때마다 상태 갱신

```json
{
  "query": "기능성 원료",
  "start_year": 2021,
  "end_year": 2026,
  "result_limit": 100,
  "classification_method": "LLM",
  "completed_steps": [
    "검색 조건 설정",
    "검색 결과 수 설정",
    "분류 방식 선택"
  ],
  "pending_steps": [
    "출력 스키마 정의",
    "검색 API 구현"
  ]
}
```

### 장점
* 중요한 요구사항을 정확하게 유지할 수 있음
* 조건 충돌과 누락을 쉽게 확인할 수 있음
* 워크플로와 연계하기 좋음
* 중단된 작업을 다시 시작하기 쉬움
* DB 저장과 버전 관리가 용이함

### 단점
* 업무별 State Schema를 설계해야 함
* 예상하지 못한 사용자 요구를 구조화하기 어려울 수 있음
* 상태 추출 및 갱신 로직이 필요함

문서 작성, 데이터 분석, 신청서 작성처럼 입력 항목과 단계가 비교적 명확한 Agent에 특히 적합합니다.

State를 갱신할 때는 전체를 매번 덮어쓰기보다 변경된 필드와 근거를 함께 관리하는 것이 좋습니다.

```json
{
  "field": "classification_method",
  "previous_value": null,
  "new_value": "LLM",
  "source": "user_message",
  "source_message_id": "msg_18"
}
```

이렇게 하면 사용자가 나중에 "아까 정한 분류 방식 바꿔줘"라고 말했을 때 어떤 값을 바꿔야 하는지 추적하기 쉽습니다.

### State 설계 기준
* 실행에 필요한 값은 명시적인 필드로 둠
* 사용자가 바꿀 수 있는 값과 시스템 내부 값을 구분함
* 기본값과 사용자가 직접 지정한 값을 구분함
* 유효하지 않은 값은 State에 반영하기 전에 검증함
* 완료된 단계와 대기 중인 단계를 분리함

### 충돌 처리 예시

```json
{
  "current_state": {
    "result_limit": 100
  },
  "new_user_input": "결과는 30개만 보면 돼",
  "updated_state": {
    "result_limit": 30
  }
}
```

State는 과거 결정사항을 보존하기 위한 장치지만, 사용자의 최신 지시가 명확하면 최신 지시를 우선해야 합니다.
