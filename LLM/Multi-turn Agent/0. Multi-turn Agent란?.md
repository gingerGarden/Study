# 0. Multi-turn Agent란?
Multi-turn Agent는 사용자와 여러 차례 대화를 주고받으면서 이전 대화의 맥락, 사용자 요구사항, 작업 진행 상태를 유지하고 다음 행동을 결정하는 LLM 기반 시스템

Single-turn LLM 호출은 현재 입력만 보고 답변을 생성하는 데 가깝지만, Multi-turn Agent는 대화가 이어지는 동안 다음 정보를 계속 관리해야 함

* 사용자가 이전에 말한 조건
* 현재까지 확정된 결정사항
* 아직 확인되지 않은 정보
* 이미 실행한 도구와 그 결과
* 다음에 수행해야 할 작업

따라서 Multi-turn Agent의 핵심은 단순히 대화 기록을 많이 넣는 것이 아니라, 현재 응답에 필요한 문맥과 상태를 선별하여 안정적으로 제공하는 것임

```

    ↓

    ↓
현재 의도 및 작업 단계 판단
    ↓

    ↓

    ↓
결과 검증 및 상태 갱신
    ↓
사용자 응답
```

## 0.1. Multi-turn Agent의 기본 구성
Multi-turn Agent는 일반적으로 다음 요소로 구성

### 0.1.1. LLM
사용자의 의도를 이해하고, 다음 행동을 결정하며, 최종 답변을 생성함

```
입력:
- 시스템 프롬프트
- 사용자 요청
- 최근 대화
- 대화 요약
- 관련 기억
- 도구 실행 결과

출력:
- 사용자 답변
- 도구 호출 요청
- 작업 상태 변경
```
LLM은 Agent의 추론 엔진 역할을 하지만, 모든 상태를 LLM 내부에만 맡기면 안정성이 떨어짐. 중요한 상태와 데이터는 애플리케이션에서 별도로 관리해야 함

LLM이 잘하는 일과 애플리케이션이 책임져야 하는 일을 구분해야 함

| 영역 | LLM이 담당하기 좋은 일 | 애플리케이션이 담당해야 하는 일 |
| --- | --- | --- |
| 의도 파악 | 자연어 요청 해석 | 허용된 의도 목록 관리 |
| 판단 | 다음 행동 후보 선택 | 정책, 권한, 입력값 검증 |
| 생성 | 사용자 응답 작성 | 원천 데이터 저장 및 변경 |
| 요약 | 대화 압축 | 요약 버전 관리 |
| 도구 사용 | 도구 호출 인자 제안 | 실제 실행, 오류 처리, 감사 로그 |


### 0.1.2. Conversation History
사용자와 Agent가 주고받은 메시지 

```py
messages = [
    {
        "role": "system",
        "content": "너는 논문 검색 지원 Agent다.",
    },
    {
        "role": "user",
        "content": "기능성 원료 관련 논문을 찾아줘.",
    },
    {
        "role": "assistant",
        "content": "검색 기간을 지정해 주세요.",
    },
    {
        "role": "user",
        "content": "최근 5년으로 해줘.",
    },
]
```
가장 단순한 Multi-turn 구현은 이전 메시지를 매 요청마다 LLM에 다시 전달하는 방식임

### 0.1.3. Agent State
Agent가 현재 어떤 작업을 수행하고 있는지를 나타내는 구조화된 상태

```json
{
  "task": "기능성 원료 논문 검색",
  "current_step": "search_condition_confirmed",
  "search_query": "기능성 원료",
  "start_year": 2021,
  "end_year": 2026,
  "result_count": 100,
  "pending_action": "search_papers"
}
```
대화 내용과 작업 상태는 구분해야 함
* 대화 이력 : 사용자와 어떤 말을 주고받았는지
* 작업 상태 : 현재 무엇이 확정되었고 다음에 무엇을 해야 하는지
Agent State를 별도로 관리하면 "그걸로 진행해", "두 번째 안으로 해줘" 같은 지시를 더 안정적으로 처리할 수 있음

State에는 가능한 한 판단 가능한 값만 저장하는 것이 좋음

```json
{
  "bad": "사용자는 최근 논문을 적당히 많이 원함",
  "good": {
    "start_year": 2021,
    "end_year": 2026,
    "result_limit": 100
  }
}
```

모호한 자연어는 대화 이력이나 요약에 남기고, 실행 조건은 구조화된 값으로 확정해야 함

### 0.1.4. Memory
* 대화 세션을 넘어 유지할 필요가 있는 정보 저장
* 예를 들면 다음과 같음

```
사용자 선호:
- 보고서 스타일의 답변을 선호함
- Python 코드에 타입 힌트를 포함하기를 원함

프로젝트 정보:
- 백엔드는 FastAPI 사용
- 기능성 소재 227개 보유
- 관련 논문 22,205건 보유
```

Memory는 일반적으로 다음과 같이 구분

| 구분                | 역할                  |
| ----------------- | ------------------- |
| Short-term Memory | 최근 대화 문맥 유지         |
| Working Memory    | 현재 작업 상태와 중간 결과     |
| Long-term Memory  | 장기간 유지할 사용자·프로젝트 정보 |
| Semantic Memory   | 의미 기반으로 검색하는 사실과 지식 |
| Episodic Memory   | 과거 대화나 작업 수행 기록     |


### 0.1.5. Tools
Agent가 LLM의 외부 기능을 사용할 수 있도록 하는 도구
예를 들어 논문 검색 Agent에는 다음과 같은 도구가 있을 수 있음

```python
search_papers(query, start_year, end_year)
get_paper_detail(paper_id)
summarize_papers(paper_ids)
save_search_result(project_id, papers)
create_report(project_id)
```

LLM은 사용자 요청을 분석해 적절한 도구와 입력값 선택

```json
{
  "tool": "search_papers",
  "arguments": {
    "query": "기능성 원료",
    "start_year": 2021,
    "end_year": 2026
  }
}
```
실제 도구 실행은 LLM이 아니라 백엔드 애플리케이션에서 수행

도구 실행 결과는 다음 응답의 중요한 근거가 되므로, 성공 여부와 원본 결과를 구분해 저장하는 것이 좋음

```json
{
  "tool": "search_papers",
  "status": "success",
  "arguments": {
    "query": "기능성 원료",
    "start_year": 2021,
    "end_year": 2026
  },
  "result_summary": "검색 결과 100건 반환",
  "raw_result_ref": "tool_result_20260729_001"
}
```

사용자에게는 요약된 결과를 보여주더라도, 재검증이나 재시도에는 원본 결과 참조가 필요함


## 0.2. 대표적인 Multi-turn 구현 방법

### 0.2.1. 전체 대화 이력 전달 방식
모든 대화 메시지를 그대로 LLM에 전달하는 방식

```python
conversation_history.append(
    {
        "role": "user",
        "content": user_input,
    }
)

response = call_llm(conversation_history)

conversation_history.append(
    {
        "role": "assistant",
        "content": response,
    }
)
```

### 장점

* 구현이 단순함
* 이전 표현과 세부 내용을 정확하게 보존함
* 초기 프로토타입에 적합함

### 단점
* 대화가 길어질수록 입력 토큰이 계속 증가함
* 비용과 응답 시간이 증가함
* 모델의 컨텍스트 길이를 초과할 수 있음
* 오래된 불필요한 정보가 현재 응답에 영향을 줄 수 있음

짧은 상담이나 내부 데모에서는 사용할 수 있지만, 장기간 사용하는 Agent에는 적합하지 않음

이 방식은 Multi-turn Agent의 출발점으로는 충분하지만, 다음 조건 중 하나라도 해당하면 다른 방식과 결합해야 함

* 세션이 20턴 이상 길어짐
* 사용자가 중간에 요구사항을 자주 수정함
* 외부 도구 호출 결과를 기반으로 다음 단계가 달라짐
* 며칠 뒤 같은 작업을 이어서 수행해야 함
* 비용이나 응답 시간이 중요한 서비스임
