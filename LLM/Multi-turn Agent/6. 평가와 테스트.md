# 6. 평가와 테스트

Multi-turn Agent는 한 번의 답변만 평가해서는 충분하지 않습니다. 여러 턴 동안 문맥을 유지하고, 상태를 올바르게 갱신하며, 도구를 안전하게 호출하는지를 평가해야 합니다.

## 6.1. 평가 대상

| 대상 | 평가 질문 |
| --- | --- |
| 문맥 유지 | 이전 조건을 정확히 기억하는가 |
| State 갱신 | 최신 사용자 지시를 구조화된 상태에 반영하는가 |
| 도구 선택 | 필요한 도구를 적절한 시점에 호출하는가 |
| 도구 입력 | 인자가 유효하고 정책을 지키는가 |
| 실패 처리 | 오류 발생 시 재시도나 확인 질문을 하는가 |
| 최종 답변 | 도구 결과와 상태에 근거해 답하는가 |
| 보안 | prompt injection이나 권한 우회를 막는가 |

## 6.2. 테스트 시나리오

Multi-turn 테스트는 대화 스크립트 형태로 작성하는 것이 좋습니다.

```json
{
  "name": "검색 조건 변경 처리",
  "turns": [
    {
      "user": "최근 5년 논문을 찾아줘.",
      "expected_state": {
        "year_range": "recent_5_years"
      }
    },
    {
      "user": "아니, 최근 3년으로 바꿔.",
      "expected_state": {
        "year_range": "recent_3_years"
      }
    }
  ]
}
```

## 6.3. 회귀 테스트

Agent는 프롬프트나 모델이 바뀌면 동작이 달라질 수 있습니다. 따라서 핵심 시나리오는 회귀 테스트로 관리해야 합니다.

회귀 테스트에 포함할 항목:

* 필수 슬롯 수집
* 조건 변경
* 도구 실패
* 결과 없음
* 장기 대화 요약
* Memory 충돌
* 민감 도구 호출 차단
* 사용자 확인이 필요한 작업

## 6.4. 평가 지표

| 지표 | 의미 |
| --- | --- |
| Task Success Rate | 사용자의 목표를 완료한 비율 |
| State Accuracy | 상태 필드가 정답과 일치하는 비율 |
| Tool Call Accuracy | 올바른 도구와 인자를 선택한 비율 |
| Recovery Rate | 실패 후 복구에 성공한 비율 |
| Clarification Quality | 필요한 경우 적절히 되묻는 비율 |
| Cost per Task | 작업 하나를 완료하는 데 든 비용 |
| Latency per Turn | 한 턴 응답 지연시간 |

정답이 하나로 고정되지 않는 답변은 LLM 평가자만 믿기보다, 상태와 도구 호출처럼 구조화된 결과를 함께 평가해야 합니다.

## 6.5. 테스트 더블

외부 API를 실제로 호출하면 테스트가 느리고 불안정해집니다. Tool Executor에는 테스트 더블을 두는 것이 좋습니다.

```python
class FakePaperSearchTool:
    def run(self, query: str, start_year: int, end_year: int) -> dict:
        return {
            "total_count": 3,
            "papers": [
                {"id": "p1", "title": "Example Paper"}
            ],
        }
```

도구 자체의 통합 테스트와 Agent 판단 테스트를 분리해야 문제 원인을 찾기 쉽습니다.
