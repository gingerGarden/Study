# 8. 운영과 모니터링

Multi-turn Agent를 실제 서비스로 운영하려면 답변 품질뿐 아니라 비용, 지연시간, 실패율, 도구 호출, 상태 변경을 관찰해야 합니다.

## 8.1. 관찰해야 할 이벤트

| 이벤트 | 설명 |
| --- | --- |
| turn_started | 사용자 입력을 받은 시점 |
| prompt_built | 프롬프트 구성이 끝난 시점 |
| llm_called | 모델 호출 정보 |
| tool_called | 도구 호출 정보 |
| state_updated | Agent State 변경 |
| memory_written | Memory 저장 |
| turn_completed | 응답 반환 완료 |
| turn_failed | 처리 실패 |

각 이벤트에는 `session_id`, `turn_id`, `user_id`, `model`, `latency_ms`, `token_usage` 같은 공통 필드를 포함하는 것이 좋습니다.

## 8.2. 핵심 운영 지표

| 지표 | 의미 |
| --- | --- |
| 평균 응답 시간 | 사용자 체감 속도 |
| P95 응답 시간 | 느린 요청 관리 |
| 토큰 사용량 | 비용 관리 |
| 도구 호출 횟수 | Agent 효율성 |
| 도구 실패율 | 외부 시스템 안정성 |
| 재시도 횟수 | 실패 복구 부담 |
| 사용자 확인 요청 비율 | 자동화 수준 |
| 작업 성공률 | Agent 품질 |

비용 최적화는 단순히 작은 모델을 쓰는 문제가 아니라, 프롬프트에 넣는 문맥을 줄이고 불필요한 도구 호출을 줄이는 문제입니다.

## 8.3. 비용 최적화

비용을 줄이는 방법:

* 최근 N턴 개수를 제한함
* 긴 도구 결과는 요약 후 참조 ID로 저장함
* Memory 검색 결과 상위 K개만 사용함
* 간단한 분류와 검증은 작은 모델을 사용함
* 복잡한 계획이나 최종 보고서에는 큰 모델을 사용함
* 캐시 가능한 결과는 재사용함

모델을 역할별로 나눌 수 있습니다.

| 역할 | 모델 선택 기준 |
| --- | --- |
| Intent Router | 빠르고 저렴한 모델 |
| State Extractor | 구조화 출력 안정성 |
| Planner | 추론 능력 |
| Executor | 도구 인자 정확도 |
| Final Writer | 문장 품질 |

## 8.4. 장애 대응

Agent 장애는 일반 API 장애보다 원인이 다양합니다.

| 증상 | 가능한 원인 |
| --- | --- |
| 응답이 느림 | 긴 프롬프트, 느린 도구, 반복 루프 |
| 이상한 답변 | 잘못된 요약, Memory 충돌, 도구 결과 누락 |
| 도구 반복 호출 | 종료 조건 부재, 관찰값 부족 |
| 비용 증가 | 최근 대화 과다, 검색 결과 원문 삽입 |
| 상태 불일치 | State 갱신 실패, 동시 요청 충돌 |

장애 분석을 위해서는 최종 답변만 저장해서는 부족합니다. 프롬프트 구성 요소, 도구 호출, 상태 변경 내역을 함께 추적해야 합니다.

## 8.5. 배포 전 체크리스트

* 최대 반복 횟수가 설정되어 있음
* 도구 입력값 검증이 있음
* 부작용 도구에는 사용자 확인이 있음
* State와 Memory 변경 로그가 있음
* 민감정보 저장 정책이 있음
* 대표 Multi-turn 시나리오 테스트가 있음
* 비용과 지연시간 모니터링이 있음
* 실패 시 사용자에게 보여줄 응답이 정의되어 있음
