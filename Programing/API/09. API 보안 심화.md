## 1. API 보안 개요
API 보안은 인증만으로 끝나지 않는다. 인증, 권한, 토큰 관리, 요청 제한, 입력값 검증, 브라우저 보안 이슈를 함께 고려해야 한다.

<br>

## 2. 인증과 인가
* 인증(Authentication): 사용자가 누구인지 확인하는 것.
* 인가(Authorization): 해당 사용자가 특정 작업을 할 권한이 있는지 확인하는 것.

예를 들어 로그인을 했다면 인증은 된 상태이다. 하지만 관리자 페이지에 접근할 수 없다면 인가에 실패한 것이다.

<br>

## 3. JWT
JWT(JSON Web Token)는 JSON 정보를 서명된 토큰 형태로 주고받는 방식이다.

JWT는 보통 세 부분으로 구성된다.

```text
header.payload.signature
```

* Header: 토큰 타입과 서명 알고리즘
* Payload: 사용자 ID, 권한, 만료 시간 같은 클레임
* Signature: 토큰 변조 여부를 검증하기 위한 서명

주의할 점:
* JWT payload는 암호화가 아니라 인코딩이다.
* 비밀번호, 주민번호 같은 민감 정보는 payload에 넣지 않는다.
* 만료 시간을 짧게 두고 재발급 전략을 설계한다.
* 서버는 signature와 만료 시간을 반드시 검증해야 한다.

<br>

## 4. OAuth 2.0 주요 흐름
OAuth 2.0은 권한 위임을 위한 표준이다. 대표적인 흐름은 Authorization Code Flow이다.

흐름:
1. 사용자가 클라이언트 앱에서 로그인 요청
2. 외부 인증 서버의 로그인/동의 화면으로 이동
3. 인증 서버가 authorization code 발급
4. 클라이언트 또는 백엔드가 code를 access token으로 교환
5. access token으로 API 호출

프론트엔드 앱에서는 PKCE를 함께 사용하는 방식이 권장된다. PKCE는 authorization code가 탈취되더라도 토큰 교환을 어렵게 만드는 보완 장치이다.

<br>

## 5. Refresh Token Rotation
Access Token은 짧게 유지하고, Refresh Token으로 새 토큰을 발급받는다.

Refresh Token Rotation은 refresh token을 사용할 때마다 새 refresh token을 발급하고, 기존 refresh token은 폐기하는 방식이다.

장점:
* 탈취된 refresh token의 재사용을 감지할 수 있음.
* 장기 로그인 기능의 보안을 높일 수 있음.

<br>

## 6. Rate Limiting
Rate Limiting은 일정 시간 동안 허용할 요청 수를 제한하는 방식이다.

예시:

```text
사용자당 1분에 100회 요청 허용
IP당 1분에 300회 요청 허용
```

제한을 초과하면 보통 `429 Too Many Requests`를 반환한다.

응답 예시:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

Rate Limiting은 비용 보호, 장애 예방, 악성 요청 방어에 사용된다.

<br>

## 7. CSRF와 XSS
CSRF(Cross-Site Request Forgery)는 사용자가 로그인된 상태를 악용해 원하지 않는 요청을 보내게 하는 공격이다.

대응:
* CSRF Token 사용
* SameSite Cookie 설정
* 중요한 변경 요청은 `GET`으로 처리하지 않음
* 상태를 변경하는 요청은 서버에서 인증과 권한을 다시 확인

XSS(Cross-Site Scripting)는 공격자가 악성 스크립트를 페이지에 삽입하는 공격이다.

대응:
* 사용자 입력값 이스케이프
* HTML 직접 삽입 최소화
* Content Security Policy 적용
* 토큰을 JavaScript에서 쉽게 접근 가능한 저장소에 보관하지 않기
* DOM 조작 시 `innerHTML`보다 `textContent` 같은 안전한 API 우선 사용

<br>

## 8. 입력값 검증
API는 클라이언트가 보낸 값을 신뢰하면 안 된다.

검증 대상:
* 필수 값 누락 여부
* 문자열 길이
* 숫자 범위
* 이메일, URL 같은 형식
* 허용되지 않은 필드
* SQL Injection, Command Injection 가능성

검증 실패 시 보통 `400 Bad Request`를 반환한다.

<br>

## 9. API 보안 체크리스트
* 인증과 인가를 구분해서 처리했는가?
* 토큰 만료 시간과 재발급 전략이 있는가?
* 민감 정보가 토큰이나 로그에 남지 않는가?
* 요청 수 제한이 있는가?
* 입력값 검증이 서버에서 수행되는가?
* HTTPS를 사용하는가?
* 브라우저 기반 API라면 CSRF, XSS 대응을 고려했는가?
