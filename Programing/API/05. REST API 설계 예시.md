## 1. REST API 설계 기본
REST API는 자원을 URL로 표현하고, HTTP 메서드로 자원에 대한 행위를 표현한다.

```text
GET /users
POST /users
GET /users/123
PATCH /users/123
DELETE /users/123
```

여기서 `users`는 자원이고, `GET`, `POST`, `PATCH`, `DELETE`는 행위이다.

<br>

## 2. 사용자 API 예시
| 기능 | 메서드 | URI | 설명 |
|----|----|----|----|
| 사용자 목록 조회 | `GET` | `/users` | 여러 사용자 조회 |
| 사용자 상세 조회 | `GET` | `/users/{id}` | 특정 사용자 조회 |
| 사용자 생성 | `POST` | `/users` | 새 사용자 생성 |
| 사용자 전체 수정 | `PUT` | `/users/{id}` | 특정 사용자 정보 전체 교체 |
| 사용자 일부 수정 | `PATCH` | `/users/{id}` | 특정 사용자 정보 일부 변경 |
| 사용자 삭제 | `DELETE` | `/users/{id}` | 특정 사용자 삭제 |

<br>

## 3. 게시글 API 예시
| 기능 | 메서드 | URI | 설명 |
|----|----|----|----|
| 게시글 목록 조회 | `GET` | `/posts` | 게시글 목록 조회 |
| 게시글 상세 조회 | `GET` | `/posts/{id}` | 특정 게시글 조회 |
| 게시글 작성 | `POST` | `/posts` | 새 게시글 작성 |
| 게시글 수정 | `PATCH` | `/posts/{id}` | 게시글 내용 변경 |
| 게시글 삭제 | `DELETE` | `/posts/{id}` | 게시글 삭제 |
| 댓글 목록 조회 | `GET` | `/posts/{postId}/comments` | 특정 게시글의 댓글 목록 조회 |
| 댓글 작성 | `POST` | `/posts/{postId}/comments` | 특정 게시글에 댓글 작성 |

<br>

## 4. URI 설계 규칙
* URI에는 동사보다 명사를 사용한다.
* 자원 이름은 보통 복수형을 사용한다.
* 계층 관계가 있으면 경로로 표현한다.
* 검색, 정렬, 페이지네이션은 Query Parameter를 사용한다.

좋은 예:

```text
GET /users
GET /users/123
GET /posts?authorId=3&page=1
```

피하는 예:

```text
GET /getUsers
POST /createUser
GET /users/list
```

HTTP 메서드가 행위를 이미 표현하므로 URI에 `get`, `create`, `delete` 같은 동사를 반복해서 넣지 않는 편이 좋다.

<br>

## 5. 요청과 응답 예시
사용자 생성 요청:

```http
POST /users
Content-Type: application/json
```

```json
{
  "name": "Kim",
  "email": "kim@example.com"
}
```

성공 응답:

```http
201 Created
Content-Type: application/json
```

```json
{
  "id": 123,
  "name": "Kim",
  "email": "kim@example.com"
}
```

## 6. REST 설계 체크리스트
* URL이 자원을 표현하는가?
* 행위는 HTTP 메서드로 표현했는가?
* 생성 성공 시 `201 Created`를 사용하는가?
* 없는 자원 조회 시 `404 Not Found`를 반환하는가?
* 인증 실패와 권한 부족을 `401`, `403`으로 구분하는가?
* 요청과 응답의 JSON 구조가 문서화되어 있는가?
