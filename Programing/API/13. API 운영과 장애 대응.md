## 1. API 운영
API는 구현 후 배포하는 것으로 끝나지 않는다. 운영 환경에서는 로그, 모니터링, 알림, 장애 대응, 배포 전략이 중요하다.

<br>

## 2. 로깅
로그는 API 요청과 처리 결과를 추적하기 위한 기록이다.

기록하면 좋은 정보:
* 요청 시간
* HTTP 메서드와 경로
* 상태 코드
* 처리 시간
* 사용자 ID 또는 요청 ID
* 에러 메시지

주의할 점:
* 비밀번호, 토큰, 카드번호 같은 민감 정보는 로그에 남기지 않는다.
* 요청마다 `requestId`를 부여하면 문제 추적이 쉬워진다.

예시:

```json
{
  "requestId": "req_123",
  "method": "GET",
  "path": "/users/1",
  "status": 200,
  "durationMs": 34
}
```

<br>

## 3. 모니터링
모니터링은 API 상태를 수치로 관찰하는 것이다.

주요 지표:
* 요청 수
* 평균 응답 시간
* p95, p99 응답 시간
* 에러율
* CPU, 메모리 사용량
* 데이터베이스 연결 수
* 외부 API 호출 실패율

평균 응답 시간만 보면 일부 느린 요청을 놓칠 수 있으므로 p95, p99 같은 지표도 함께 본다.

<br>

## 4. 알림
장애를 빠르게 알기 위해 알림 기준을 정한다.

예시:
* 5xx 에러율이 5분 동안 3% 초과
* p95 응답 시간이 2초 초과
* 데이터베이스 연결 실패 증가
* 외부 결제 API 실패율 증가

알림은 너무 민감하면 피로도가 높아지고, 너무 둔감하면 장애를 늦게 알게 된다.

<br>

## 5. Health Check
Health Check는 서버가 정상 동작하는지 확인하는 API이다.

```text
GET /health
```

응답 예시:

```json
{
  "status": "ok"
}
```

더 깊은 점검이 필요하면 데이터베이스, 캐시, 외부 API 연결 상태를 함께 확인한다.

<br>

## 6. Circuit Breaker
Circuit Breaker는 외부 시스템 장애가 전체 서비스 장애로 번지는 것을 막는 패턴이다.

예를 들어 결제 API가 계속 실패하면 일정 시간 동안 호출을 중단하고 즉시 실패 응답을 반환한다. 이후 일정 시간이 지나면 다시 일부 요청을 보내 회복 여부를 확인한다.

상태:
* Closed: 정상 호출
* Open: 호출 차단
* Half-Open: 일부 요청으로 회복 확인

<br>

## 7. 장애 대응 절차
1. 장애 감지
2. 영향 범위 확인
3. 임시 완화 조치
4. 원인 분석
5. 재발 방지 조치
6. 장애 보고서 작성

장애 대응에서 가장 중요한 것은 사용자의 피해를 줄이는 것이다. 원인 분석은 서비스 영향 완화 이후에 진행해도 된다.

<br>

## 8. 운영 체크리스트
* 요청 로그에 requestId가 있는가?
* 민감 정보가 로그에 남지 않는가?
* 에러율과 응답 시간을 모니터링하는가?
* Health Check API가 있는가?
* 외부 API 장애에 대한 timeout, retry, circuit breaker가 있는가?
* 장애 발생 시 알림과 대응 절차가 정해져 있는가?
