## 1. API 문서화
API 문서는 API를 사용하는 사람이 요청과 응답 규칙을 정확히 이해할 수 있도록 정리한 문서이다.

API 문서에는 보통 다음 내용이 포함된다.

* API 기본 주소
* 인증 방식
* 엔드포인트 목록
* HTTP 메서드
* 요청 파라미터
* 요청 본문 예시
* 응답 본문 예시
* 상태 코드
* 에러 응답 형식

<br>

## 2. OpenAPI
OpenAPI는 REST API를 표준 형식으로 설명하는 명세이다. 사람이 읽는 문서뿐 아니라 도구가 읽을 수 있는 API 계약서 역할도 한다.

OpenAPI 문서를 작성하면 다음을 할 수 있다.

* Swagger UI로 API 문서 화면 생성
* 클라이언트 코드 생성
* 서버 코드 골격 생성
* API 테스트 자동화
* 프론트엔드와 백엔드 간 계약 공유

<br>

## 3. OpenAPI 예시
```yaml
openapi: 3.0.3
info:
  title: User API
  version: 1.0.0
servers:
  - url: https://api.example.com
paths:
  /users/{id}:
    get:
      summary: 사용자 상세 조회
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        "200":
          description: 조회 성공
          content:
            application/json:
              schema:
                type: object
                properties:
                  id:
                    type: integer
                  name:
                    type: string
                  email:
                    type: string
        "404":
          description: 사용자를 찾을 수 없음
```

<br>

## 4. Swagger
Swagger는 OpenAPI 명세를 기반으로 API 문서를 보여주거나 테스트할 수 있게 해주는 도구 생태계이다.

대표 도구:
* Swagger UI: OpenAPI 문서를 웹 화면으로 보여줌.
* Swagger Editor: OpenAPI 문서를 작성하고 검증함.
* Swagger Codegen: 명세를 기반으로 코드를 생성함.

<br>

## 5. 좋은 API 문서의 조건
* 실제 동작과 문서가 일치해야 한다.
* 요청 예시와 응답 예시가 있어야 한다.
* 필수 값과 선택 값을 구분해야 한다.
* 인증 방식과 권한 조건을 명확히 적어야 한다.
* 실패 응답도 성공 응답만큼 자세히 문서화해야 한다.
* 버전 변경 사항을 기록해야 한다.

<br>

## 6. 문서화 체크리스트
* 모든 엔드포인트가 문서에 있는가?
* 파라미터 타입과 필수 여부가 명확한가?
* 상태 코드별 응답이 문서화되어 있는가?
* 공통 에러 형식이 설명되어 있는가?
* 문서와 실제 구현을 함께 검증하는 절차가 있는가?
