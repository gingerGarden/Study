## 1. API 버전 관리
API는 한 번 공개되면 여러 클라이언트가 의존하게 된다. 따라서 변경할 때 기존 클라이언트가 깨지지 않도록 버전 관리와 하위 호환성을 고려해야 한다.

<br>

## 2. Breaking Change
Breaking Change는 기존 클라이언트가 정상 동작하지 않게 만드는 변경이다.

예시:
* 기존 응답 필드 삭제
* 필드 타입 변경
* 필수 요청 파라미터 추가
* 기존 상태 코드 의미 변경
* 기존 URL 제거

가능하면 Breaking Change는 피하고, 필요하다면 새 버전을 제공한다.

<br>

## 3. Non-Breaking Change
기존 클라이언트를 깨지 않는 변경이다.

예시:
* 응답 필드 추가
* 새 엔드포인트 추가
* 선택 요청 파라미터 추가
* 더 구체적인 에러 메시지 추가

클라이언트는 모르는 응답 필드가 추가되어도 깨지지 않도록 구현하는 것이 좋다.

<br>

## 4. URL 기반 버전 관리
```text
GET /v1/users
GET /v2/users
```

장점:
* 버전이 URL에 보여 이해하기 쉽다.
* 라우팅과 문서화가 단순하다.

단점:
* URL이 API 버전에 강하게 묶인다.
* 작은 변경에도 버전이 늘어날 수 있다.

<br>

## 5. Header 기반 버전 관리
```http
GET /users
Accept: application/vnd.example.v2+json
```

또는:

```http
API-Version: 2
```

장점:
* URL을 자원 중심으로 유지할 수 있다.
* 버전 협상이 가능하다.

단점:
* 브라우저나 단순 테스트 도구에서 확인이 덜 직관적이다.
* 문서화와 디버깅이 복잡해질 수 있다.

<br>

## 6. 하위 호환성 전략
* 기존 필드를 바로 삭제하지 않고 deprecated 상태로 둔다.
* 제거 예정일을 문서와 응답 헤더로 알린다.
* 새 필드를 추가하고 기존 필드는 일정 기간 유지한다.
* 클라이언트별 사용 현황을 로그로 확인한 뒤 제거한다.
* 변경 이력을 changelog로 관리한다.

예시:

```http
Deprecation: true
Sunset: Wed, 31 Dec 2026 23:59:59 GMT
```

<br>

## 7. 버전 관리 체크리스트
* 변경이 Breaking Change인지 판단했는가?
* 기존 클라이언트의 영향 범위를 확인했는가?
* deprecated 기간을 제공하는가?
* 문서와 changelog를 업데이트했는가?
* 새 버전과 기존 버전을 동시에 운영할 계획이 있는가?
