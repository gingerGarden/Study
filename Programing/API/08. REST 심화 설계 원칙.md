## 1. REST 심화 개념
REST API를 제대로 설계하려면 URL과 HTTP 메서드만 맞추는 것에서 끝나지 않는다. HTTP 메서드의 의미, 멱등성, 캐싱 가능성, 일관된 자원 표현까지 함께 고려해야 한다.

<br>

## 2. Safe Method
Safe Method는 서버의 데이터를 변경하지 않는 메서드이다.

| 메서드 | Safe 여부 | 설명 |
|----|----|----|
| `GET` | O | 자원 조회 |
| `HEAD` | O | 응답 본문 없이 헤더만 조회 |
| `OPTIONS` | O | 서버가 지원하는 요청 방식 확인 |
| `POST` | X | 자원 생성 또는 처리 |
| `PUT` | X | 자원 전체 수정 |
| `PATCH` | X | 자원 일부 수정 |
| `DELETE` | X | 자원 삭제 |

`GET` 요청은 조회만 해야 한다. `GET /users/delete/1`처럼 조회 메서드로 삭제를 수행하면 HTTP 의미를 어기게 된다.

<br>

## 3. Idempotency
Idempotency는 같은 요청을 여러 번 보내도 결과가 같아야 한다는 성질이다.

| 메서드 | 멱등 여부 | 예시 |
|----|----|----|
| `GET` | O | 여러 번 조회해도 서버 상태는 같음 |
| `PUT` | O | 같은 내용으로 여러 번 교체해도 결과는 같음 |
| `DELETE` | O | 이미 삭제된 자원을 다시 삭제해도 최종 상태는 같음 |
| `POST` | 보통 X | 같은 요청을 여러 번 보내면 여러 개 생성될 수 있음 |
| `PATCH` | 설계에 따라 다름 | 증가 연산이면 멱등하지 않을 수 있음 |

예시:

```http
PUT /users/1
Content-Type: application/json
```

```json
{
  "name": "Kim",
  "email": "kim@example.com"
}
```

위 요청은 여러 번 보내도 사용자 1의 최종 상태가 동일하므로 멱등적이다.

<br>

## 4. Pagination
목록 API는 데이터가 많아질 수 있으므로 페이지네이션이 필요하다.

Offset 방식:

```text
GET /posts?page=1&size=20
GET /posts?offset=0&limit=20
```

* 장점: 구현이 쉽고 특정 페이지 이동이 편함.
* 단점: 데이터가 많거나 중간에 데이터가 추가/삭제되면 성능과 일관성이 떨어질 수 있음.

Cursor 방식:

```text
GET /posts?cursor=eyJpZCI6MTAwfQ&limit=20
```

* 장점: 큰 데이터셋에서 성능이 좋고 실시간 데이터에 강함.
* 단점: 특정 페이지 번호로 바로 이동하기 어렵다.

응답 예시:

```json
{
  "items": [
    { "id": 101, "title": "API 기초" },
    { "id": 100, "title": "HTTP 이해" }
  ],
  "page": {
    "size": 20,
    "nextCursor": "eyJpZCI6MTAwfQ",
    "hasNext": true
  }
}
```

<br>

## 5. Filtering과 Sorting
검색 조건과 정렬은 Query Parameter로 표현한다.

```text
GET /orders?status=paid&sort=createdAt,desc&page=1&size=20
```

* `status=paid`: 결제 완료 주문만 조회
* `sort=createdAt,desc`: 생성일 기준 내림차순 정렬
* `page=1&size=20`: 1페이지, 20개 조회

필터와 정렬 규칙은 API 문서에 명확히 적어야 한다.

<br>

## 6. HATEOAS
HATEOAS는 응답 안에 다음에 수행할 수 있는 행동의 링크를 포함하는 REST 제약 조건이다.

```json
{
  "id": 1,
  "name": "Kim",
  "links": {
    "self": "/users/1",
    "orders": "/users/1/orders"
  }
}
```

실무에서는 모든 API가 HATEOAS를 엄격히 지키지는 않는다. 다만 자원의 관계와 다음 행동을 링크로 표현할 수 있다는 개념은 알아두는 것이 좋다.

<br>

## 7. REST 심화 체크리스트
* `GET` 요청이 서버 데이터를 변경하지 않는가?
* `PUT`, `DELETE` 요청이 멱등성을 가지는가?
* 목록 API에 페이지네이션이 있는가?
* 필터, 정렬, 검색 규칙이 일관적인가?
* 응답 구조가 확장 가능하게 설계되어 있는가?
