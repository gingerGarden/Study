## 1. API 성능
API 성능은 응답 속도뿐 아니라 처리량, 안정성, 비용까지 포함한다. 좋은 API는 빠르게 응답하고, 트래픽이 증가해도 안정적으로 동작해야 한다.

<br>

## 2. 캐싱
캐싱은 자주 요청되는 데이터를 임시 저장해 반복 처리 비용을 줄이는 방식이다.

캐싱 위치:
* 브라우저 캐시
* CDN
* 프록시 서버
* 애플리케이션 메모리
* Redis 같은 캐시 저장소

HTTP 캐시 헤더 예시:

```http
Cache-Control: public, max-age=60
```

위 헤더는 응답을 60초 동안 캐시할 수 있다는 의미이다.

<br>

## 3. ETag
ETag는 응답 데이터의 버전을 나타내는 값이다. 클라이언트는 기존에 받은 ETag를 서버에 보내 데이터가 바뀌었는지 확인할 수 있다.

첫 번째 응답:

```http
HTTP/1.1 200 OK
ETag: "user-1-v3"
```

이후 요청:

```http
GET /users/1
If-None-Match: "user-1-v3"
```

데이터가 바뀌지 않았다면 서버는 본문 없이 응답할 수 있다.

```http
HTTP/1.1 304 Not Modified
```

<br>

## 4. 압축
JSON 응답이 크면 gzip이나 br 압축을 사용해 전송량을 줄일 수 있다.

```http
Content-Encoding: gzip
```

압축은 네트워크 비용을 줄이지만 CPU 사용량이 늘 수 있으므로 응답 크기와 트래픽을 고려해 적용한다.

<br>

## 5. N+1 문제
N+1 문제는 목록을 조회한 뒤 각 항목마다 추가 쿼리를 실행해 성능이 급격히 나빠지는 문제이다.

예시:
1. 게시글 20개 조회
2. 각 게시글의 작성자 조회를 위해 20번 추가 쿼리
3. 총 21번 쿼리 실행

해결 방법:
* join 사용
* batch loading
* 필요한 데이터를 한 번에 조회
* GraphQL에서는 DataLoader 같은 도구 사용

<br>

## 6. GraphQL Query Complexity
GraphQL은 클라이언트가 원하는 구조를 직접 요청할 수 있어 유연하지만, 지나치게 복잡한 쿼리가 서버에 부담을 줄 수 있다.

대응:
* 쿼리 깊이 제한
* 쿼리 비용 계산
* 요청 시간 제한
* 페이지네이션 강제
* 허용된 쿼리만 실행하는 persisted query 사용

<br>

## 7. Timeout과 Retry
API 호출은 무한정 기다리면 안 된다.

* Timeout: 일정 시간 안에 응답이 없으면 실패 처리
* Retry: 일시적 오류일 때 재시도

주의할 점:
* `POST`처럼 멱등하지 않은 요청은 재시도 시 중복 생성이 발생할 수 있다.
* 재시도 간격을 점점 늘리는 exponential backoff를 사용한다.
* `429`, `503` 응답에서는 `Retry-After` 헤더를 확인한다.
* 결제나 주문 생성처럼 중복 처리가 위험한 요청에는 idempotency key를 사용할 수 있다.
