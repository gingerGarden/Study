## 분산 버전 관리 시스템(DVCS)

### 1. 개요

DVCS(Distributed Version Control System)는 코드와 문서의 변경 이력을 저장하고, 여러 사람이 같은 프로젝트를 안정적으로 작업할 수 있게 해 주는 버전 관리 방식이다.

Git은 대표적인 DVCS이다. Git을 사용하면 단순히 파일을 백업하는 수준을 넘어, 언제 무엇이 바뀌었는지 추적하고, 특정 시점으로 돌아가고, 여러 작업 흐름을 브랜치로 분리하고, 원격 저장소를 통해 협업할 수 있다.

<br>

### 2. 중앙 집중식 버전 관리와 DVCS의 차이

#### 2.1. 중앙 집중식 버전 관리 시스템

중앙 집중식 버전 관리 시스템(CVCS)은 중앙 서버에 프로젝트 이력이 있고, 개발자는 필요한 파일을 내려받아 작업한다.

* 예시: Subversion(SVN), CVS
* 장점: 구조가 비교적 단순하고 권한 관리를 중앙에서 하기 쉬움
* 단점: 중앙 서버에 접속하지 못하면 많은 작업이 제한됨
* 단점: 중앙 서버에 장애가 생기면 전체 작업 흐름이 영향을 받을 수 있음

#### 2.2. 분산 버전 관리 시스템

DVCS는 각 개발자가 전체 저장소 이력을 로컬에 복제해서 가진다.

* 예시: Git, Mercurial
* 로컬에서 커밋, 브랜치 생성, 로그 조회, 비교, 되돌리기 가능
* 원격 저장소는 협업과 백업을 위한 공유 지점 역할을 함
* 중앙 서버가 잠시 없어도 로컬 저장소의 이력은 유지됨

<br>

### 3. Git이 파일을 관리하는 방식

Git은 파일의 최종 결과만 저장하는 것이 아니라, 커밋이라는 단위로 프로젝트의 상태를 기록한다.

#### 3.1. 스냅샷 모델

Git의 커밋은 특정 시점의 프로젝트 스냅샷이다.

* 파일이 바뀌면 새 스냅샷에 변경된 상태가 기록됨
* 바뀌지 않은 파일은 이전 상태를 효율적으로 재사용함
* 각 커밋은 이전 커밋과 연결되어 이력을 형성함

#### 3.2. 커밋 해시

각 커밋은 고유한 해시 값을 가진다.

* 예시: `a1b2c3d`
* 해시는 특정 커밋을 가리키는 식별자임
* `git log`에서 커밋 해시를 확인할 수 있음
* 되돌리기, 비교, 특정 시점 확인에 사용됨

#### 3.3. HEAD

`HEAD`는 현재 내가 보고 있는 커밋 또는 브랜치를 가리키는 포인터이다.

* 보통은 현재 체크아웃한 브랜치의 최신 커밋을 가리킴
* 브랜치를 이동하면 `HEAD`도 함께 이동함
* 특정 커밋으로 직접 이동하면 detached HEAD 상태가 될 수 있음

<br>

### 4. Git의 주요 공간

Git을 다룰 때는 파일이 어느 공간에 있는지 이해하는 것이 중요하다.

#### 4.1. 워킹 디렉토리

현재 실제로 파일을 수정하는 작업 공간이다.

* 에디터에서 수정하는 파일들이 여기에 있음
* 아직 Git에 기록되지 않은 변경도 포함됨

#### 4.2. 스테이징 영역

다음 커밋에 포함할 변경 사항을 준비하는 공간이다.

* `git add`로 워킹 디렉토리의 변경 사항을 스테이징함
* 커밋에 포함할 변경만 골라 담을 수 있음
* 같은 파일 안에서도 일부 변경만 스테이징할 수 있음

#### 4.3. 로컬 저장소

내 컴퓨터 안에 있는 Git 저장소이다.

* `.git` 디렉토리에 Git 이력이 저장됨
* `git commit`을 하면 스테이징 영역의 내용이 로컬 저장소에 기록됨
* 인터넷 없이도 대부분의 Git 작업이 가능함

#### 4.4. 원격 저장소

GitHub, GitLab, Bitbucket 같은 서버에 있는 공유 저장소이다.

* 여러 사람이 변경 사항을 주고받는 기준점
* `git push`로 로컬 커밋을 업로드함
* `git fetch` 또는 `git pull`로 원격 변경을 가져옴

<br>

### 5. 기본 작업 흐름

Git의 기본 흐름은 다음 순서로 이해하면 된다.

1. 파일을 수정한다.
2. `git status`로 변경 상태를 확인한다.
3. `git add`로 커밋할 변경을 스테이징한다.
4. `git commit`으로 로컬 저장소에 기록한다.
5. `git push`로 원격 저장소에 공유한다.
6. 다른 사람이 올린 변경은 `git pull`로 가져온다.

흐름을 공간 기준으로 표현하면 다음과 같다.

```text
워킹 디렉토리 --git add--> 스테이징 영역 --git commit--> 로컬 저장소 --git push--> 원격 저장소
원격 저장소 --git fetch/pull--> 로컬 저장소
```

<br>

### 6. 브랜치와 병합의 개념

브랜치는 독립적인 작업 흐름을 만들기 위한 이름 있는 포인터이다.

* `main`: 보통 안정적인 기본 브랜치
* `feature/login`: 로그인 기능 개발 브랜치 예시
* `fix/header-bug`: 버그 수정 브랜치 예시

브랜치를 사용하면 아직 완성되지 않은 작업을 기본 브랜치와 분리할 수 있다.

#### 6.1. 병합

병합은 한 브랜치의 변경 사항을 다른 브랜치에 합치는 작업이다.

* Fast-forward 병합: 현재 브랜치가 단순히 앞으로 이동해도 되는 경우
* 3-way 병합: 두 브랜치가 서로 다른 커밋을 가지고 있어 공통 조상을 기준으로 합치는 경우
* 충돌: 같은 부분을 서로 다르게 수정해서 Git이 자동으로 합칠 수 없는 경우

#### 6.2. rebase

`rebase`는 내 브랜치의 시작점을 다른 커밋 위로 옮겨 이력을 정리하는 작업이다.

* 장점: 커밋 이력을 직선에 가깝게 정리할 수 있음
* 주의: 이미 원격에 공유한 커밋을 함부로 rebase하면 협업자에게 문제가 생길 수 있음

초보 단계에서는 공유된 브랜치에서는 `merge`를 기본으로 사용하고, `rebase`는 개인 작업 브랜치에서 신중하게 사용하는 것이 좋다.

<br>

### 7. 충돌이 발생하는 이유

충돌(conflict)은 Git이 자동으로 어떤 변경을 선택해야 할지 판단할 수 없을 때 발생한다.

대표적인 상황은 다음과 같다.

* 두 사람이 같은 파일의 같은 줄을 다르게 수정함
* 한 사람은 파일을 삭제했고 다른 사람은 같은 파일을 수정함
* 브랜치가 오래 분리되어 있어 변경 차이가 커짐

충돌은 Git 사용 실패가 아니다. 협업 중 자연스럽게 발생할 수 있는 상황이며, 파일을 열어 어떤 내용을 남길지 결정한 뒤 다시 커밋하면 된다.

<br>

### 8. DVCS의 장점과 주의점

#### 8.1. 장점

* 로컬 작업 속도가 빠름
* 인터넷 없이도 커밋과 브랜치 작업 가능
* 브랜치 생성과 병합이 유연함
* 각 개발자가 전체 이력을 보유하므로 백업 효과가 있음
* 실험적인 작업을 별도 브랜치에서 안전하게 진행 가능

#### 8.2. 주의점

* 처음에는 워킹 디렉토리, 스테이징 영역, 로컬 저장소, 원격 저장소 구분이 헷갈릴 수 있음
* 저장소 전체 이력을 복제하므로 큰 저장소는 용량이 커질 수 있음
* 이미 공유한 커밋을 수정하거나 강제 푸시하면 협업자에게 영향을 줄 수 있음
* 충돌 해결 방법을 익혀야 안정적으로 협업할 수 있음

<br>

### 9. Git을 사용할 때의 기본 원칙

* 작업 전에는 `git status`로 현재 상태를 확인한다.
* 원격 변경이 있을 수 있으면 작업 전 또는 push 전에 `git pull`을 고려한다.
* 커밋은 너무 크지 않게, 하나의 의미 있는 변경 단위로 만든다.
* 커밋 메시지는 무엇을 왜 바꿨는지 알 수 있게 작성한다.
* 실험이나 기능 개발은 새 브랜치에서 진행한다.
* `git push -f`는 협업 브랜치에서 사용하지 않는다.
* 명령 실행 전 내가 어느 브랜치에 있는지 확인한다.
