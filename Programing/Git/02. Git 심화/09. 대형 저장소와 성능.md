# 대형 저장소와 성능

저장소가 커지면 clone, status, checkout, fetch가 느려질 수 있다. Git 전문가는 저장소 구조와 도구 선택으로 성능 문제를 줄일 수 있어야 한다.

## 1. 저장소 크기 확인

```bash
git count-objects -vH
```

디렉토리 크기 확인:

```bash
du -sh .git
```

큰 파일 이력은 저장소 크기를 빠르게 키운다.

## 2. Git LFS

대형 바이너리 파일은 Git LFS를 사용한다.

```bash
git lfs install
git lfs track "*.psd"
git add .gitattributes
git add design.psd
git commit -m "Track design files with Git LFS"
```

Git LFS는 파일 자체를 일반 Git 객체로 저장하지 않고 포인터를 저장한다.

주의:

* 원격 저장소가 LFS를 지원해야 함
* 저장 용량과 트래픽 제한을 확인해야 함
* 이미 커밋한 대형 파일은 별도 이력 정리가 필요함

## 3. shallow clone

최근 이력만 가져온다.

```bash
git clone --depth 1 https://github.com/username/repository.git
```

CI처럼 전체 이력이 필요 없는 환경에서 유용하다.

## 4. sparse checkout

저장소 일부 경로만 체크아웃한다.

```bash
git sparse-checkout init --cone
git sparse-checkout set src docs
```

monorepo에서 필요한 디렉토리만 작업할 때 유용하다.

## 5. partial clone

필요한 객체를 나중에 받아오는 방식이다.

```bash
git clone --filter=blob:none https://github.com/username/repository.git
```

대형 저장소 clone 시간을 줄일 수 있다.

## 6. gc와 maintenance

Git 객체 정리:

```bash
git gc
```

자동 유지보수:

```bash
git maintenance start
```

일반 사용자는 자주 직접 실행할 필요가 없지만, 저장소가 매우 커졌거나 느려졌을 때 확인한다.

## 7. 성능을 해치는 습관

* 빌드 산출물을 커밋함
* 로그 파일을 커밋함
* 대형 바이너리를 일반 Git으로 커밋함
* 불필요한 generated file을 대량 커밋함
* `.gitignore` 없이 의존성 디렉토리를 커밋함

## 8. 예방

* `.gitignore`를 프로젝트 초기에 작성
* 대형 파일은 LFS 검토
* generated file은 원칙적으로 커밋하지 않음
* 저장소 크기를 주기적으로 확인
* CI에서는 shallow clone 또는 partial clone 검토
