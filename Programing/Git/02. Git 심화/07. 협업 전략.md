# 협업 전략

Git 전문가에게는 명령어 지식뿐 아니라 팀에 맞는 이력 관리 전략을 선택하는 능력이 필요하다.

## 1. 전략 선택 기준

브랜치 전략은 다음 기준으로 선택한다.

* 배포 빈도
* 팀 규모
* 코드 리뷰 방식
* 릴리스 유지보수 필요 여부
* 자동화 테스트와 CI 수준
* hotfix 대응 방식

## 2. Feature Branch Workflow

기능마다 브랜치를 만들고 PR로 병합하는 방식이다.

흐름:

```bash
git switch main
git pull origin main
git switch -c feature-login
```

작업 후:

```bash
git push -u origin feature-login
```

장점:

* 이해하기 쉬움
* 코드 리뷰와 잘 맞음
* 대부분의 팀에서 무난함

주의:

* 브랜치가 오래 살아 있으면 충돌이 커짐
* 자주 main을 반영해야 함

## 3. Git Flow

장기 릴리스 브랜치가 필요한 프로젝트에서 사용된다.

주요 브랜치:

* `main`: 배포된 안정 버전
* `develop`: 다음 릴리스 개발
* `feature/*`: 기능 개발
* `release/*`: 릴리스 준비
* `hotfix/*`: 긴급 수정

장점:

* 릴리스 관리가 명확함
* 유지보수 버전이 많은 프로젝트에 적합함

주의:

* 브랜치 구조가 복잡함
* 빠른 배포 환경에는 무거울 수 있음

## 4. Trunk-Based Development

짧은 브랜치를 사용하고 자주 main에 통합하는 방식이다.

특징:

* 브랜치를 짧게 유지
* 작은 단위로 자주 병합
* feature flag와 자동 테스트가 중요함

장점:

* 통합 충돌이 작아짐
* 지속적 배포와 잘 맞음

주의:

* 테스트 자동화가 약하면 위험함
* 미완성 기능을 숨기는 전략이 필요함

## 5. Squash merge, merge commit, rebase merge

Squash merge:

* PR의 여러 커밋을 하나로 합침
* main 이력이 단순해짐
* 개별 커밋 이력은 사라짐

Merge commit:

* 브랜치 이력을 그대로 보존
* 병합 지점이 명확함
* 이력이 복잡해질 수 있음

Rebase merge:

* 이력을 직선에 가깝게 유지
* 커밋 단위가 잘 정리된 팀에 적합함
* 충돌 해결 이력이 덜 드러날 수 있음

## 6. 커밋 단위 원칙

좋은 커밋:

* 하나의 이유로 변경됨
* 빌드와 테스트를 깨지 않음
* 메시지만 봐도 의도를 알 수 있음
* 리뷰하기 쉬운 크기임

나쁜 커밋:

* 포맷팅, 기능 변경, 리팩터링이 뒤섞임
* 메시지가 `fix`, `update`처럼 모호함
* 너무 커서 리뷰하기 어려움

## 7. PR 전 확인

```bash
git status
git log --oneline --decorate --graph origin/main..HEAD
git diff origin/main...HEAD
```

확인할 것:

* 의도한 파일만 바뀌었는가?
* 불필요한 로그나 secret이 들어갔는가?
* 커밋 메시지가 읽을 만한가?
* 최신 main과 충돌이 없는가?
