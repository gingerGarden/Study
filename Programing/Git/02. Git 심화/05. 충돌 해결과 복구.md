# 충돌 해결과 복구

Git 전문가에게 중요한 능력은 문제가 생기지 않게 하는 것이 아니라, 문제가 생겼을 때 상태를 정확히 읽고 복구하는 것이다.

## 1. 충돌의 종류

대표적인 충돌:

* content conflict: 같은 줄을 다르게 수정
* add/add conflict: 양쪽에서 같은 경로에 서로 다른 파일 추가
* modify/delete conflict: 한쪽은 수정, 한쪽은 삭제
* rename/delete conflict: 한쪽은 이름 변경, 한쪽은 삭제
* binary conflict: 이미지나 바이너리 파일 충돌

## 2. 충돌 상태 확인

```bash
git status
```

충돌 파일만 보기:

```bash
git diff --name-only --diff-filter=U
```

충돌 단계 확인:

```bash
git ls-files -u
```

## 3. ours와 theirs

merge 상황:

* ours: 현재 브랜치
* theirs: 병합하려는 브랜치

특정 파일에서 현재 브랜치 내용 선택:

```bash
git checkout --ours 파일명
git add 파일명
```

병합하려는 브랜치 내용 선택:

```bash
git checkout --theirs 파일명
git add 파일명
```

rebase 상황에서는 ours/theirs의 의미가 직관과 다르게 느껴질 수 있다. rebase 중에는 기준 브랜치 쪽이 ours, 다시 적용 중인 내 커밋이 theirs로 보일 수 있으므로 `git status`와 diff를 확인한다.

## 4. merge 중단

```bash
git merge --abort
```

## 5. rebase 중단

```bash
git rebase --abort
```

## 6. reflog

`reflog`는 HEAD와 브랜치가 어디를 가리켰는지 기록한다. 실수로 커밋이 사라진 것처럼 보여도 reflog에서 찾을 수 있다.

```bash
git reflog
```

예시 복구:

```bash
git reflog
git switch -c rescue a1b2c3d
```

또는 현재 브랜치를 특정 시점으로 되돌림:

```bash
git reset --hard a1b2c3d
```

주의: `reset --hard`는 현재 작업 내용을 버릴 수 있다.

## 7. dangling commit 찾기

참조되지 않는 커밋을 찾을 때:

```bash
git fsck --lost-found
```

찾은 커밋 확인:

```bash
git show <커밋해시>
```

브랜치로 보호:

```bash
git branch rescue <커밋해시>
```

## 8. 잘못 삭제한 브랜치 복구

브랜치 삭제 후 커밋 해시를 알고 있거나 reflog에서 찾았다면:

```bash
git branch 복구브랜치명 <커밋해시>
```

## 9. 복구 전 안전 조치

불안하면 현재 상태를 먼저 브랜치로 저장한다.

```bash
git branch backup-before-recovery
```

또는 작업 중인 변경을 stash한다.

```bash
git stash push -m "backup before recovery"
```
