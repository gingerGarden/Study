# 보안과 운영

Git 저장소는 코드뿐 아니라 조직의 운영 리스크와도 연결된다.

## 1. secret을 커밋하지 않기

커밋하면 안 되는 예:

* API key
* access token
* private key
* `.env`
* 인증서
* 운영 DB 접속 정보

`.gitignore` 예:

```gitignore
.env
*.pem
*.key
secrets/
```

## 2. secret을 이미 커밋했을 때

가장 먼저 해야 할 일은 이력 삭제가 아니라 secret 폐기이다.

순서:

1. 노출된 key나 token을 즉시 revoke 또는 rotate한다.
2. 새 secret을 발급한다.
3. 저장소 이력에서 제거할지 판단한다.
4. 팀원에게 re-clone 또는 이력 정리 절차를 안내한다.

이미 공개된 secret은 Git 이력에서 지워도 안전해지지 않는다.

## 3. 이력에서 민감정보 제거

전문 도구를 사용한다.

* `git filter-repo`
* BFG Repo-Cleaner

주의:

* 이력을 재작성하므로 모든 커밋 해시가 바뀔 수 있음
* 모든 협업자가 기존 클론을 정리해야 함
* 원격 저장소의 캐시나 PR 기록에도 흔적이 남을 수 있음

## 4. signed commit

커밋 서명을 사용하면 커밋 작성자를 검증할 수 있다.

```bash
git commit -S -m "Add signed commit"
```

항상 서명:

```bash
git config --global commit.gpgsign true
```

서명 검증:

```bash
git log --show-signature
```

## 5. signed tag

릴리스 태그에는 서명을 고려한다.

```bash
git tag -s v1.0.0 -m "Release v1.0.0"
git tag -v v1.0.0
```

## 6. protected branch

원격 저장소에서 기본 브랜치를 보호한다.

권장 규칙:

* 직접 push 금지
* PR 리뷰 필수
* CI 통과 필수
* force push 금지
* branch deletion 금지

## 7. 운영 사고 예방 습관

* push 전 `git diff --staged` 확인
* PR 전 secret 검색 도구 사용
* 대형 파일은 Git LFS 사용 검토
* main에는 직접 push하지 않음
* force push는 개인 브랜치에서도 이유를 확인함
