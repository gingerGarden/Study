# 이력 편집 심화

이력 편집은 Git 전문가에게 필수지만, 협업 중에는 위험할 수 있다. 핵심은 "공유된 이력인가?"를 먼저 판단하는 것이다.

## 1. 원칙

* 공유하지 않은 로컬 커밋은 자유롭게 정리할 수 있음
* 이미 push했고 다른 사람이 받을 수 있는 커밋은 신중하게 다룸
* 공유된 커밋을 취소할 때는 `revert`를 우선 사용함
* 이력을 바꿔야 한다면 팀과 합의하고 `--force-with-lease`를 사용함

## 2. reset의 세 가지 모드

`reset`은 브랜치가 가리키는 커밋을 옮긴다.

```bash
git reset --soft HEAD~1
```

* 커밋만 취소
* 변경은 스테이징 영역에 남음

```bash
git reset --mixed HEAD~1
```

* 커밋 취소
* 변경은 워킹 디렉토리에 남음
* 기본 모드

```bash
git reset --hard HEAD~1
```

* 커밋 취소
* 변경도 버림
* 실행 전 반드시 확인 필요

## 3. revert

`revert`는 기존 커밋을 없애지 않고 반대 변경을 담은 새 커밋을 만든다.

```bash
git revert <커밋 해시>
```

공유된 브랜치에서 안전하다.

merge commit을 revert할 때는 mainline parent를 지정해야 할 수 있다.

```bash
git revert -m 1 <머지커밋해시>
```

## 4. interactive rebase

여러 로컬 커밋을 정리할 때 사용한다.

```bash
git rebase -i HEAD~3
```

주요 명령:

* pick: 커밋 유지
* reword: 메시지 수정
* edit: 커밋 중간에서 멈춤
* squash: 이전 커밋과 합치고 메시지 편집
* fixup: 이전 커밋과 합치고 메시지 버림
* drop: 커밋 제거

사용 예:

* 작은 수정 커밋들을 하나로 합치기
* 커밋 메시지 정리
* 커밋 순서 조정

주의: 이미 공유한 커밋에는 신중하게 사용한다.

## 5. commit 분리

하나의 커밋에 여러 변경이 섞였을 때 분리할 수 있다.

```bash
git reset HEAD~1
git add -p
git commit -m "첫 번째 의미 있는 변경"
git add -p
git commit -m "두 번째 의미 있는 변경"
```

## 6. cherry-pick의 충돌

특정 커밋만 가져올 때 충돌이 날 수 있다.

```bash
git cherry-pick <커밋해시>
```

충돌 해결 후:

```bash
git add 충돌파일명
git cherry-pick --continue
```

중단:

```bash
git cherry-pick --abort
```

## 7. 안전한 강제 push

강제 push가 꼭 필요하다면 `--force-with-lease`를 사용한다.

```bash
git push --force-with-lease
```

이 옵션은 내가 모르는 원격 변경이 있으면 push를 막아 준다.

## 8. 위험 명령을 실행하지 말아야 하는 상황

`git push -f`를 피해야 하는 상황:

* 팀원이 함께 사용하는 기본 브랜치인 경우
* 원격 변경을 `fetch`로 확인하지 않은 경우
* push 거절 메시지를 단순히 우회하려는 경우
* CI나 배포 브랜치 이력을 바꿀 수 있는 경우

`git reset --hard`를 피해야 하는 상황:

* 커밋하지 않은 작업이 남아 있는 경우
* 어떤 커밋으로 이동하는지 확실하지 않은 경우
* 복구용 브랜치나 stash가 없는 경우

실행 전 확인:

```bash
git status
git log --oneline --decorate --graph -n 10
git diff
```

안전 조치:

```bash
git branch backup-before-history-edit
git stash push -m "backup before history edit"
```
