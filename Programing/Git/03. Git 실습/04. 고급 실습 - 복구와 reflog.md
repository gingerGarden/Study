# 고급 실습 - 복구와 reflog

목표:

* `reset --hard`로 사라진 것처럼 보이는 커밋을 복구할 수 있다.
* detached HEAD에서 만든 커밋을 브랜치로 보호할 수 있다.
* `reflog` 출력 의미를 해석할 수 있다.

## 1. 준비

```bash
mkdir git-recovery-practice
cd git-recovery-practice
git init
printf "one\n" > data.txt
git add data.txt
git commit -m "Add one"
printf "two\n" >> data.txt
git add data.txt
git commit -m "Add two"
git log --oneline
```

예상 출력:

```text
b2c3d4e Add two
a1b2c3d Add one
```

## 2. 실수로 hard reset

```bash
git reset --hard HEAD~1
git log --oneline
```

예상 출력:

```text
a1b2c3d Add one
```

해석:

* `Add two` 커밋이 일반 로그에서는 보이지 않는다.
* 아직 완전히 사라진 것은 아닐 수 있다.

## 3. reflog로 찾기

```bash
git reflog
```

예상 출력 일부:

```text
a1b2c3d HEAD@{0}: reset: moving to HEAD~1
b2c3d4e HEAD@{1}: commit: Add two
```

복구:

```bash
git branch rescue-add-two b2c3d4e
git switch rescue-add-two
git log --oneline
```

해석:

* `reflog`는 HEAD가 과거에 가리켰던 위치를 보여 준다.
* 커밋 해시를 찾으면 브랜치를 만들어 보호할 수 있다.

## 4. detached HEAD 복구

```bash
git switch main
git switch --detach HEAD
printf "detached work\n" >> data.txt
git add data.txt
git commit -m "Work in detached HEAD"
git switch -c rescue-detached
```

해석:

* detached HEAD에서 만든 커밋은 브랜치 이름이 없으면 잃어버리기 쉽다.
* 바로 `git switch -c`로 브랜치를 만들면 안전하다.

## 5. 점검 문제

* `git log`에 안 보이는 커밋이 `git reflog`에는 보일 수 있는 이유는 무엇인가?
* 복구할 커밋을 찾았을 때 바로 `reset --hard`하기보다 브랜치를 만드는 것이 왜 안전한가?
